## 1. Архітектурний опис

### Вибір моделі та інструментів
Для ядра класифікатора обрано модель **OpenAI `gpt-4o-mini`**. Основний аргумент — ідеальний баланс між вартістю, швидкістю (latency) та якістю логічного висновку (reasoning) для задачі маршрутизації в реальному часі. 
* **Ціна/Якість:** Модель коштує орієнтовно $0.15 за 1М вхідних токенів, що дозволяє обробляти тисячі тікетів щоденно з мінімальними витратами для бізнесу (менше 1 цента за тікет). 
* **Швидкість:** Відповідь генерується майже миттєво, що критично для забезпечення низького часу очікування (SLA) у системі підтримки Nebula.
* **Відмова від Fine-tuning:** На етапі MVP донавчання власної моделі є економічно недоцільним (overengineering). `gpt-4o-mini` у комбінації з якісним промптингом забезпечує точність понад 90% "з коробки", залишаючись гнучкою до змін бізнес-вимог.

### Структура промпту та гарантія формату
Система побудована на концепції **System Prompt + JSON Mode + Pydantic Contract**:
1. **JSON Mode:** Виклик API жорстко налаштований на `response_format={"type": "json_object"}`. Це вимикає "балакучість" моделі і змушує її повертати виключно сирі дані.
2. **Few-Shot Prompting:** У System Prompt зашиті правила поведінки та конкретні приклади (Input -> Expected Output). Це задає патерн розпізнавання складних тікетів без зміни коду.
3. **Pydantic Validation:** Відповідь LLM автоматично проганяється через Pydantic BaseModel (`TicketClassificationResult`). Якщо модель спробує повернути неіснуюче поле або порушити структуру, Pydantic згенерує помилку, яка буде безпечно оброблена оркестратором.

### Визначені категорії тікетів
Бізнес-логіка маршрутизації розподіляє звернення на такі категорії:
* `Bug` — технічні проблеми з додатком.
* `Refund` — запити на повернення коштів.
* `Subscription` — питання щодо скасування або подовження підписки.
* `Expert_Complaint` — невдоволення якістю консультації астролога (специфіка Nebula).
* `General_Question` — загальні питання щодо функціоналу.
* `Safety_Risk` — екстрені випадки (загроза життю, шантаж).

### Мітигація помилок та Hallucinations (Fail-Safe архітектура)
Оскільки LLM є ймовірнісною системою, я заклав архітектуру безпечного збою (Fault Tolerance). Якщо виникає галюцинація (модель вигадала категорію), таймаут мережі або вичерпання лімітів API, система **не падає**. 
Замість цього блок `try...except` перехоплює `ValidationError` або `APIError` і викликає метод `_build_fallback_result()`. Тікету автоматично призначається статус, який примусово направляє його на ручне опрацювання (Fallback). Жодне звернення користувача не губиться в системі.

## 2. Межі автоматизації (Human-in-the-loop)

### Тікети, які не підлягають автоматизації
Впроваджуючи AI у продукт ніші астрології та психології (Nebula), ми стикаємося з високим рівнем емоційності користувачів. Автоматизація наступних категорій є небезпечною з репутаційної та юридичної точок зору:
1. **Загроза життю (Safety Risks):** Повідомлення про депресію, суїцидальні наміри або селф-харм. AI не має емпатії і може надати шаблонну відповідь, що є неприпустимим. Такі тікети вимагають негайного втручання людини та застосування екстрених протоколів.
2. **Агресія та токсичність:** Лайка, погрози судом або образи експертів. Вимагають ручного review для можливого бану користувача або деескалації конфлікту.
3. **Іноземні мови (Non-English):** В рамках MVP обмежуємо ШІ англійською мовою. Переклад на льоту збільшує споживання токенів та ризик хибної інтерпретації контексту.

### Механізм Human-in-the-loop (HITL)
Для збереження контролю над ШІ я імплементував архітектуру Human-in-the-loop через булевий прапорець **`needs_human`**.
* **Як це працює:** LLM працює виключно як маршрутизатор (Tier-1). Якщо модель класифікує тікет як звичайний (наприклад, просте питання про підписку), `needs_human` залишається `False`. 
* **Ескалація:** Якщо в тексті виявляється тригер (нецензурна лексика, інша мова, незрозумілий контекст), LLM переводить прапорець у `True`. Для випадків `Safety_Risk` система додатково маркує тікет як `priority: CRITICAL`.
* **Інтеграція з Helpdesk:** Будь-який тікет із позначкою `needs_human: True` або тікет, що пройшов через системний Fallback, миттєво виводиться з контуру автоматичних відповідей і потрапляє у пріоритетну чергу до живого оператора.

## 3. Еволюція промпту

### Початковий (наївний) промпт
На старті розробки MVP я використовував базовий Zero-Shot підхід. Промпт виглядав приблизно так:
> *"You are a customer support assistant for the Nebula app. Classify the user's ticket into one of the following categories: Bug, Refund, Subscription, Expert_Complaint, General_Question, Safety_Risk. Return the result in JSON format with fields: category, priority, needs_human."*

**Проблеми цього підходу:**
1. **Нестабільна структура:** Іноді модель повертала JSON, обгорнутий у Markdown-блоки (````json ... ````), що ламало парсинг на бекенді.
2. **Галюцинації значень:** Модель могла придумати власні рівні пріоритету (наприклад, `priority: "URGENT"` замість дозволеного `HIGH`).
3. **Плутанина в категоріях:** Модель не розуміла тонкої межі між скасуванням підписки (`Subscription`) і запитом на повернення коштів (`Refund`).

### Фінальна версія промпту
Перехід до структурованого контракту з використанням **Few-Shot Prompting** та жорстким заданням правил. Фінальна логіка промпту:
1. **Роль та Контекст:** Чітке позиціювання (Support AI for Nebula).
2. **Strict Output Schema:** Явна вимога повертати лише валідний JSON без жодного додаткового тексту (закріплено на рівні API через `response_format={"type": "json_object"}`).
3. **Definitions & Rules:** Детальний опис кожної категорії. Наприклад: *"Refund is ONLY when the user explicitly asks for money back. If they just want to cancel future payments, it is Subscription."*
4. **Few-Shot Examples:** Додано 3-4 приклади пар "Складний вхідний текст -> Ідеальний вихідний JSON", що змушує модель копіювати патерн.

**Чому це покращило результат:**
Few-Shot Prompting фактично виконує роль "мікро-навчання" в контексті одного запиту. Модель перестала вгадувати формат і почала діяти за наочним шаблоном. Чіткі визначення категорій усунули похибку (Accuracy зросла з ~70% до 91.7%).

## 4. Обробка Edge Cases

Під час тестування на синтетичних даних я виявив кілька критичних крайових випадків (Edge Cases), з якими базова LLM не справлялася коректно.

### Кейс 1: Токсичність та агресія користувача
* **Ситуація:** Користувач пише: *"This app is a f**king scam, your astrologers are liars, delete my account!"*.
* **Неочікуваний результат:** AI спокійно класифікував це як `General_Question` або `Expert_Complaint` зі статусом `needs_human: false`. Це небезпечно, оскільки автоматична стандартна відповідь розлютила б користувача ще більше.
* **Рішення:** У System Prompt було додано жорстке правило безпеки: *"If the text contains profanity, extreme anger, or legal threats, YOU MUST set `needs_human: true`"*. Тепер такі тікети миттєво ескалюються до менеджерів.

### Кейс 2: Змішаний інтент (Bug + Refund)
* **Ситуація:** Тікет містить кілька проблем одночасно: *"The app crashed right during my premium reading. I lost my money, give me a refund!"*
* **Неочікуваний результат:** AI не міг обрати одну категорію і генерував невалідне значення на кшталт `Bug_Refund`, що ламало наш Enum.
* **Рішення:** Я впровадив ієрархію пріоритетів у промпті. Додано інструкцію: *"If multiple intents are present, prioritize financial requests (Refund) and Safety Risks over technical issues (Bug)"*. Тепер система чітко фокусується на найкритичнішому для бізнесу аспекті тікета.

### Кейс 3: Неанглійські звернення (Non-English)
* **Ситуація:** Користувач пише іспанською: *"Quiero un reembolso"*.
* **Неочікуваний результат:** Модель автоматично перекладала текст, класифікувала його як `Refund` і ставила `needs_human: false`. Але наш бот для автоматичних відповідей (наступний етап пайплайну) спілкується лише англійською.
* **Рішення:** Додано тригер визначення мови. Якщо мова не англійська, класифікатор зберігає категорію, але примусово ставить `needs_human: true`, щоб тікет потрапив до відповідного локалізованого саппорту.

## 5. Власні архітектурні рішення (Fail-Safe Validation)

Одним із ключових архітектурних рішень, яке **я прийняв особисто** під час проєктування MVP, була відмова від стандартного парсингу JSON (`json.loads()`) на користь жорсткої валідації через Pydantic-схеми з імплементацією патерну **Graceful Degradation (Fallback)**.

**Обґрунтування рішення:**
Більшість розробників-початківців довіряють параметру `json_object` від OpenAI і вважають, що повернуті дані завжди будуть правильними. Але з точки зору бекенд-інженерії, LLM — це *недетермінована система*. Вона є зовнішнім, ненадійним I/O ресурсом.

Я спроєктував систему так, щоб вона ставилася до відповіді LLM як до "недовірених даних" (untrusted data):
1. **Абсолютний бар'єр:** Я створив Pydantic модель `TicketClassificationResult` зі строго типізованими Enum-класами. Коли LLM повертає рядок, я пропускаю його через `model_validate_json()`. Якщо ШІ згалюцинує категорію або забуде повернути обов'язкове поле `priority`, Pydantic миттєво викине `ValidationError`.
2. **Перехоплення та Fallback:** Замість того, щоб дозволити цій помилці обвалити мікросервіс (Crash), я імплементував перехоплювач на рівні оркестратора (`try...except`). У разі будь-якої помилки (галюцинація LLM, таймаут мережі, відмова API OpenAI), мій код генерує **Fallback-об'єкт**.
3. **Бізнес-цінність:** Fallback примусово задає тікету `priority: HIGH` та `needs_human: True`. 

**Результат:** Моє рішення гарантує 100% Fault Tolerance. Навіть якщо інфраструктура OpenAI повністю впаде, жоден тікет користувача не буде втрачений (dropped) чи залишений без відповіді — система безпечно деградує до ручного режиму обробки, забезпечуючи безперервність бізнес-процесів Nebula.

| "Quiero un reembolso" | `Refund` (needs_human: True) | `Refund` (needs_human: True) | ✅ Pass | Тригер неанглійської мови спрацював, тікет направлено на ручну обробку. |

### Cost Analysis (Прогноз на 10k тікетів)
Модель `gpt-4o-mini` оптимізована для економічної маршрутизації.
* **Ціна одного тікета:** Середній промпт (інструкція + тікет) займає ~300 вхідних токенів. Відповідь (JSON) — ~20 вихідних токенів. Вартість одного запиту становить приблизно **$0.000057**.
* **Прогноз на 10,000 тікетів/місяць:** $0.000057 × 10,000 = **~$0.57 на місяць**.
* **Оптимізація вартості:** Вартість вже є мінімальною. Подальша оптимізація можлива лише шляхом використання Prompt Caching для статичної частини інструкції.

### Стратегія Caching
* **Чи потрібен кеш результатів?** Ні. Кешувати зв'язку `ticket_text -> category` недоцільно, оскільки користувачі формулюють запити унікально. Збіги "символ у символ" майже не трапляються.
* **Що саме кешувати?** На рівні OpenAI API активно використовується **Prompt Caching** для `SYSTEM_PROMPT`. Оскільки інструкція та Few-Shot приклади є статичними, вони кешуються на серверах OpenAI, що додатково знижує latency на 50% і вартість вхідних токенів удвічі при високому навантаженні.
* **Інвалідація:** Кеш промпту інвалідується автоматично з боку провайдера або під час деплою нової версії інструкцій класифікатора.
