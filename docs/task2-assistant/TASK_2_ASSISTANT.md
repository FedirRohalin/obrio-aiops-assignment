# Task 2: Архітектура AI Support Assistant

## 1. Архітектура системи та Workflow

AI Support Assistant — це синхронний pipeline для ефективної обробки тікетів служби підтримки. Workflow має послідовну архітектуру:

1. **Input:** тікет клієнта надходить через Command Line Interface (CLI).
2. **Retrieval:** BM25 Retriever шукає найрелевантніші статті у внутрішній Knowledge Base.
3. **Processing:** `LLMClient` формує структурований prompt і викликає LLM API. Запит обгорнуто в Tenacity retries для обробки тимчасових збоїв мережі або API.
4. **Output:** LLM повертає суворо типізовану JSON-відповідь, що містить категорію тікета, запропоноване рішення та точні цитати.


---



## 2. Стратегія Retrieval (BM25)

Для пошуку документів обрано алгоритм BM25 замість векторних embeddings (наприклад, cosine similarity з OpenAI embeddings).

- **Швидкість та ефективність:** BM25 працює повністю локально в пам'яті, що усуває зовнішні API-виклики та зменшує latency.
- **Вартість:** витрати на embeddings відсутні.
- **Придатність:** для невеликої та добре структурованої Knowledge Base точний збіг за ключовими словами й тегами, який забезпечує BM25, дає високу точність retrieval без семантичного overhead векторних баз даних.


---


## 3. Prompt Engineering та Caching

Дизайн prompt оптимізовано під безпеку, вартість і строго структурований вивід.

- **Статичний System Prompt:** використовується максимально статичний `SYSTEM_PROMPT`. Це підвищує hit rate Prompt Caching від OpenAI та суттєво знижує latency і вартість токенів при повторних inference-запитах.
- **Ізоляція контексту через XML-теги:** для мітигації ризику prompt injection дані користувача та системний контекст суворо розділені XML-тегами. Отримані статті інкапсульовано в `<knowledge_base>`, а користувацький ввід ізольовано в `<ticket>`.


---


## 4. Resilience та запобігання галюцинаціям

Надійність і фактична точність є критичними для процесів підтримки. Система забезпечує їх такими механізмами:

- **Fallback-механізми:** `LLMClient` використовує бібліотеку Tenacity для автоматичних retries з exponential backoff. Це забезпечує стійкість до rate limits і тимчасової недоступності API.
- **Strict Citation Contract:** щоб запобігти галюцинаціям LLM, вихідну схему суворо типізовано за допомогою `pydantic`. Додатково post-generation валідація на Python примусово застосовує strict citation contract: кожна цитата, повернена LLM, програмно перевіряється на те, що вона є точним substring відповідної статті з Knowledge Base.

## 5. Evaluation, Cost Forecast & Caching

### Оцінка моделей (Evaluation)
Систему оцінено за допомогою автоматичного прогону `run_eval.py` на зафіксованому датасеті. Результати бенчмарку:

| Input (Тип тікета) | Expected Article | Actual (gpt-4o-mini) | Pass/Fail | Latency |
| :--- | :--- | :--- | :---: | :--- |
| Password Reset | `KB-101` | `KB-101` | ✅ Pass | 2.94 s |
| Duplicate Charge | `KB-201` | `KB-201` | ✅ Pass | 3.08 s |
| App Crash | `KB-301` | `KB-301` | ✅ Pass | 3.20 s |
| Delete Account | `KB-401` | `KB-401` | ✅ Pass | 2.57 s |

*Усі галюцинації формату або цитування, якщо такі виникали під час тестування, успішно пригнічувалися через `pydantic` та повторні виклики (Repair Retries).*

### Cost Analysis (Прогноз на 10k тікетів)
Як production-модель обрано `gpt-4o-mini`. Вона приблизно **в 16 разів дешевша** за `gpt-4o` ($0.001215 проти $0.019575 на наборі з 4 тікетів).
* **Ціна одного тікета:** Включає контекст бази знань та генерацію трьох варіантів відповідей. Середня вартість становить **~$0.0003**.
* **Прогноз на 10,000 тікетів/місяць:** $0.0003 × 10,000 = **~$3.00 на місяць**.
* **Оптимізація вартості:** Вартість утримується на мінімальному рівні завдяки використанню BM25 (відсутність плати за embeddings) та агресивному Prompt Caching.

### Стратегія Caching
* **Що кешувати:** У цьому кейсі найефективнішим є **API-level Prompt Caching**. Статичний `SYSTEM_PROMPT` із правилами генерації тональностей передається на початку кожного запиту, що дозволяє OpenAI кешувати його.
* **Кешування Knowledge Base:** Розглядалася можливість кешування всієї бази знань у промпті, але від неї відмовилися на користь BM25 Retrieval. BM25 гарантує, що в контекст потрапляють лише релевантні статті, економлячи токени генерації.
* **Інвалідація:** Якщо база знань оновлюється (додано нові правила повернення коштів), BM25 індекс перезбирається під час старту застосунку, гарантуючи, що LLM завжди працює з актуальними даними.

## 6. Trade-offs та обмеження автоматизації

Попри прискорення обробки запитів, система працює в жорстких межах:

- **Відсутність прямої взаємодії з клієнтом:** система працює як agent-assist інструмент і не надсилає відповіді клієнтам напряму.
- **Read-Only контекст:** асистент не інтегрований із live production-базами даних. Він не може верифікувати стан користувача в реальному часі (наприклад, перевірити фактичний баланс рахунку чи історію транзакцій).
- **Обов'язковий human-in-the-loop:** через ці обмеження участь агента підтримки (human-in-the-loop) залишається обов'язковою. Агент має переглянути згенерований AI чернетку відповіді, верифікувати фактичний статус акаунта клієнта та виконати всі необхідні дії, що змінюють стан системи (наприклад, оформлення повернення коштів).
